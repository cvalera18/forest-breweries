# Forest Breweries

A two-screen Flutter app that lists breweries from the [Open Brewery DB](https://www.openbrewerydb.org/) and shows their details. The list is sorted by distance to the user.

## How to run

Requirements: Flutter 3.41 (Dart 3.11) and an Android emulator or device.

```bash
flutter pub get
flutter run
```

```bash
flutter test
```

The code generated by `injectable` (`injection.config.dart`) is committed, so there's no need to run `build_runner` to launch the app. If you change any DI annotation:

```bash
dart run build_runner build
```

> Tested on Android (emulator, API 36). The iOS setup is included (location permission in `Info.plist`), but I couldn't verify it because I developed on Windows.

## What I completed

**Core requirements**

- **Paginated list** (name, type and city) with infinite scroll. Loading, error with retry, and empty states.
- **Visible errors without losing data:** if the first page fails, a full-screen error with *Retry*. If a later page fails, the list is kept and the error shows at the bottom with its own *Retry*.
- **Detail screen** that fetches the brewery by id and shows its name, address, phone and website, with "Not available" when a field is missing.
- **Layered architecture** (domain / data / presentation), organized by feature.
- **Typed exceptions:** the repository maps Dio and parsing errors to a `sealed class AppException` (network, not found, server, unexpected). The Bloc and Cubit turn them into states; the UI picks the message with an exhaustive `switch`.
- **DI** with get_it + injectable. The service locator is only used in `main.dart` and the router; screens get their Bloc through `BlocProvider`.
- **Tests:** bloc_test for the list and the detail (Loading → Success / Error, pagination, fallback without location), plus tests for the repository's error mapping, the DTO, and Haversine.

**Bonus: distance**

- On launch, the app asks for location (**approximate** only) and the list comes sorted by proximity, with the distance on each card.
- Sorting is done by the **API** (`by_dist`), not the client: sorting a paginated list on the client would only sort what's already loaded. Haversine is used to **display** the distance.
- If location isn't available (permission denied or blocked, GPS off, or no fix within 10 s), the list still shows in the default order, with a banner explaining how to enable it and the right action (ask again or open Settings). When the user comes back from Settings, the app checks again on its own.

## Decisions and trade-offs

- **Bloc for the list, Cubit for the detail.** Scrolling fires "load more" many times in a row; with Bloc, `droppable()` from bloc_concurrency drops repeated requests while a page is loading. The detail has a single action (load or retry), so a Cubit is enough.
- **Exceptions instead of `Either`/`Result`**, because the brief asks for it and because with a `sealed class` the compiler guarantees that no error type goes unhandled.
- **No use cases.** Here they would only forward the call to the repository. I'd add them once there's business logic combining repositories.
- **DTO separate from the entity.** The DTO mirrors the API (snake_case, everything nullable, the type as a string); the entity uses safe types (`BreweryType` as an enum, with `unknown` for new API values).
- **Hand-written `fromJson`** instead of `json_serializable`: it's 12 fields, and it shows explicitly how each null is handled. With more models I'd use the generator.
- **Distance by default instead of a toggle.** The API's default order is alphabetical, which doesn't help the user. Since location is the purpose of the screen, I ask for it on launch, and if it isn't available the app degrades gracefully without blocking anything.
- **Last known position only if it's under 5 minutes old.** It's instant, but it can be stale. If it isn't recent, a fresh one is requested with a time limit.
- **Callback-based navigation.** The list only reports which brewery was tapped; the router decides where to navigate.

## What I intentionally left out

- **Pull-to-refresh, map, search and offline mode.** The brief asks for a single, well-executed bonus.
- **Widget and integration tests.** I focused on the logic (states, pagination, errors), which is where the edge cases are.
- **Pixel-perfect UI, authentication and CI/CD**, out of scope per the brief.

## What I'd improve with more time

Ordered by how much each would add to the app:

1. **Pull-to-refresh** that keeps the list if the reload fails.
2. **Mapbox map**, with breweries as markers and selection by tapping one.
3. **Search with debounce**, to quickly find a specific brewery.
4. **Cache of the last list**, to show it instantly when the app opens offline.
5. **Tappable phone and website** with `url_launcher`.

## Structure

```
lib/
  app/                 MaterialApp and router (composition root)
  core/
    di/                get_it + injectable
    error/             AppException
    location/          Coordinates, Haversine, LocationService
    network/           Dio setup and DioException mapping
    widgets/           ErrorView
  features/breweries/
    domain/            Brewery entity and repository contract
    data/              DTO, remote data source and repository
    presentation/      Bloc/Cubit, screens and widgets
```
